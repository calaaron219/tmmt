**Phase 3 — Time System** ✅
- **PR #20** — Task CRUD. `/app/time` with quick-add form, list, status toggle, delete. `Task` model with `priority` (LOW/MED/HIGH), `status` (TODO/IN_PROGRESS/DONE/CANCELED), `estimateMinutes`, `dueAt`. Show-completed toggle via `?show=all`.
- **PR #21** — Time tracking. `TimeEntry` model + start/stop timer per task. Single active timer per user (decision 2.1) enforced via transaction. Per-task tracked total shown in metadata row; live ticker (client-side `setInterval`) on the running entry. Six PR-level sub-decisions captured in `docs/decisions/phase-3-time-system.md`.
- **PR #22** — Projects. `Project` model + nullable `Task.projectId` (`onDelete: SetNull`). CRUD at `/app/time/projects`. **Subtle 3px colored left border** on task rows that have a project (project-less tasks stay visually flat). URL filter uses `"none"` literal for project-less; per-task project re-assignment deferred. 5 decisions in `docs/decisions/phase-3-projects.md`.
- **PR #23** — Routines (DAILY-only). `Routine` model + nullable `Task.routineId` (`onDelete: SetNull`). **Lazy generation** on `/app/time` page load via `ensureTodayRoutineTasksForUser` (no worker yet). Per-routine transaction with in-tx re-check of `lastGeneratedFor` for concurrent-tab safety. UTC midnight day boundary. CRUD at `/app/time/routines`. No `cadence` field — adding it later defaulting to DAILY stays backwards-compatible.
- **PR #24** — Week-view calendar. `TimeBlock` model (kept separate from `TimeEntry` — planned vs. actual). `/app/time/calendar` hand-rolled 7-column × 16-row grid (6am–10pm). Click empty hour cell → create-block form; click existing → edit/delete; drag bottom edge → resize (pointer events, 15-min snap, touch-friendly). Single-day blocks only in v1 (no midnight crossing). `react-big-calendar` deferred to a future swap per decision #2.
- **PR #25** — AI day planner (Gemini). `LlmPlanner` interface as a **sibling** to `LlmCategorizer` (per decision #4). `apps/web/src/lib/ai-planner.ts` mirrors `ai-categorizer.ts`. Two-step UX: `planMyDay()` returns a non-persisted proposal; `applyPlan()` validates per-row and batch-creates `TimeBlock`s. Working window 09:00–18:00 UTC (narrower than the calendar grid, intentional). Post-model sanity pass drops proposals that overlap, fall outside the window, reference unknown tasks, or are <5 min.

## Top open questions (ask the user next session)

1. **Phase 4 ordering** — worker first (NestJS + BullMQ + Redis), or per-user TZ first? Worker-first is cleaner architecturally; TZ-first ships a visible quality-of-life win sooner.
2. **Cron host** — Railway's built-in cron, or BullMQ Repeatable Job? BullMQ keeps everything in one runtime; Railway cron is one less moving piece. Has trade-offs for retry semantics.
3. **Subscription detector heuristic** — pure rules (same merchant + ~28-day interval + ~same amount) for v1, or rules → AI fallback like the categorizer? AI feels heavy here; recurring patterns are mostly deterministic.
4. **AI planner adoption signal** — after a week of real use, is the 09–18 working window the right default? If not, schedule the TZ + working-hours pref PR earlier than planned.
